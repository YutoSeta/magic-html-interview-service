# Magic HTML Contracts

Executable API and data contracts shared by the independently deployed Magic HTML services.

This repository is the only allowed compile-time dependency shared by every service. It contains no provider implementation, database model, or orchestration logic.

## Dependency tiers

- Tier 0: atomic capabilities (`image`, `video`, `slide`, `wireframe`, `presentation`, `document`, `static-compiler`)
- Tier 1: independent domain services (`content`, `collection`, `media`, `forms`, `design-context`, `styler`, `neo-styler`, `illustration`, `interview`, `knowledge`, `crm`, `messaging`, `channel`, `measurement`, `site-source`, `site-import`, `site-edit`, `preview`, `approval`)
- Tier 2: immutable publication assembly, multi-page site composition, and approval-gated `site-change` orchestration
- Tier 3: deterministic StaticSite build and approval-gated deployment operations (`build` then `release`)
- Product layer: Composer and its admin UI

Dependencies point from a higher tier to a lower tier. A lower tier must never import or call a higher tier, and cycles are forbidden. Tier 3 has ordered `build` and `release` substages so Deploy can re-resolve a Static Builder artifact without permitting the reverse dependency.

## Versioning

Every payload carries `contract_version`. Additive changes may remain in `v1`; removing or changing the meaning of a field requires a new major contract directory and endpoint prefix.

Run the repository checks with:

```bash
composer test
```

The OpenAPI descriptions are split into `openapi/tier0.json` through `openapi/tier3.json`. Individual JSON Schemas are in `schemas/v1` and are suitable for generated clients and contract fixtures. Provider calls and orchestration that can exceed an HTTP request deadline use the common asynchronous job model.

A Static Builder manifest digest has one canonical byte representation. Sort `files` by `path` in bytewise ascending order, concatenate `path + NUL + lowercase sha256 + NUL` for every file, then encode the SHA-256 of those concatenated bytes as lowercase hexadecimal. File size, content, and JSON serialization are not part of this digest input.

Static compilation may bind a supplied raster asset to an existing element ID as a finite `decorative_background`. The binding is explicit, page-scoped, asset-path-scoped, and limited to fixed fit, position, and repeat enums. It does not accept arbitrary HTML, CSS, selectors, scripts, or an inferred placement decision; missing pages, elements, assets, duplicate IDs, and conflicting targets fail closed.

Content, Collection, and Media have separate databases and deployment environments. Their published snapshot versions are assembled by the Tier 2 Publication service into one self-contained immutable document. Referenced media bytes are copied into Publication-owned storage and integrity checked, so a later StaticSite build never depends on a live Content, Collection, Media, or legacy aggregate CMS API.

Media also accepts bounded private document-vault objects for text, Markdown, HTML, CSV, OOXML, and SQLite. These document types are authenticated attachment downloads only and never enter the public publication surface; consumers must inspect opaque bytes independently before parsing them. An unpublished media delete is confirmation-required and succeeds only after both object bytes and metadata are absent. Partial deletion failures are hidden from metadata, preview, public, and publish reads while remaining retryable; published objects are immutable and return 409.

Site Composer accepts independent `image_limit` and `video_limit` budgets. Generated binary media is imported into the composed site's immutable asset set rather than retaining an AI provider's temporary output URL.

Composer's product-layer authoring API exposes the same finite `insert`, `move`, `update`, `remove`, and `duplicate` AST operations used by its DnD editor. A mutation is an atomic batch of at most 25 operations against a revision-pinned snapshot: the body carries `base_revision`, while matching strong `If-Match` and replay-safe `Idempotency-Key` values remain HTTP headers. Artifact discovery and revision history are bounded and omit document bodies; full documents are returned only by snapshot and mutation results. Restore is append-only: it copies an old document into a new revision without rewriting history or publishing HTML. The transport contracts deliberately keep the Vocabulary AST open because finite vocabulary, root, realization, and HTML grammar validation belong to the owning Composer host rather than this provider-neutral package.

Styler's staged Design AST path uses one immutable Stage Bundle across layout, skin, decor, and motion. The bundle is the minimum refinement context: annotated semantic HTML, bindings, design brief, viewports, and every completed stage's AST and compiled CSS are transported together with canonical SHA-256 digests. CSS by itself is intentionally not a valid downstream or refinement input. The orchestration result retains the four ASTs separately, while its CSS is the deterministic ordered compilation of their owned layers.

Legacy pipeline contracts `1.1` and `1.2` require caller-supplied compact (at most 480 CSS pixels wide) and wide (at least 1024 CSS pixels wide) viewport contexts. Contract `1.3` instead requires one integrity-bound, frozen Layout Snapshot page reference and prohibits detached `page_key`, HTML, viewports, and legacy approved-layout payloads. Its bounded quality review records target coverage, contrast where palette values are machine-readable, decoration density, and motion duration; a hard finding may consume the shared refinement budget, while checks that require a rendered browser remain explicit diagnostics rather than being inferred from CSS alone.

Design Context is produced upstream of Styler and Neo Styler. The independent Design Context service derives portable Design DNA from design-interview text, renders that DNA as two prose documents (the design direction that page authoring reads, and the canvas brief that canvas generation reads — both restricted to what the DNA and interview say), renders a digest-bound Design Canvas for one viewport (`desktop` or `mobile`) and one framing (`site-top` or `landing`; a landing page is made mobile first, then desktop with the mobile canvas as `style_reference`), lists Canvas-grounded decorative assets, and generates only explicitly selected plan items. Planning never generates images implicitly. Styler consumes DNA, Canvas, and selected assets as references. Under contract `1.3`, the Common Layout and semantic structure are already frozen upstream: Styler deterministically hydrates the exact Layout AST/CSS without a Layout LLM or structure-editing step, then owns only the reversible Skin, Decor, and Motion loops. Contracts `1.1` and `1.2` alone retain the legacy Styler Layout generation/import behavior.

The canonical contracts for these five independent operations live under `schemas/v1/design-context/` and are exposed in the Tier 1 OpenAPI as `/v1/design-dna-jobs`, `/v1/design-direction-jobs`, `/v1/design-canvas-jobs`, `/v1/decorative-asset-plan-jobs`, `/v1/decorative-asset-jobs` and `/v1/jobs/{job}`. `schemas/v1/styler/design-context.json` remains the closed, digest-bound handoff contract consumed by Styler; it does not imply that Styler owns the upstream artifacts.

Neo Styler is a Tier 1 page authoring capability that takes the opposite bet from Styler: a model writes each page's HTML and CSS directly, and the contract makes the seat belts explicit instead of forbidding the markup. Every word on a page is a named slot derived from a Site AST (`schemas/v1/neo-styler/site-ast.json`: pages, collections, navigation placement, the top page's digest, and for `site.type: landing` the CV) and content (`content.json`: the hero, each page's and each collection item's sections); the model sees slot names such as `section-<key>-title`, `section-<key>-items-<n>-text` or `hero-image`, never values, so it cannot rewrite or add copy. A destination is never a raw `href`, `path` or `url` field (those are refused) but a `link { label, target, to }` whose `target` is `form`, `section`, `external`, `tel` or `mail`; the service resolves it to `#<form>`, `#<section key>`, the URL, `tel:` or `mailto:`, exposes it as `-link-text` / `-link-href` slots, and adds `target="_blank" rel="noopener"` to external links itself. Images are `{ aspect, mime, transparent, prompt }` specs that become image slots and are returned as `image_requests` for the caller to generate and bind. Header, hamburger, footer, breadcrumb, sub-hero, CTA band, CV bar and forms are fixed HTML computed from the Site AST that the model may only style. Authoring proceeds top page first, then a lead sub page chained off the top's response, then the remaining pages in parallel, then the first item of each collection with the rest expanded without a model; each page is judged deterministically (browser render at 320px and 1280px, slot usage, links outside the slots, fixed parts rendered with worst-case copy) and regenerated with the findings until it passes or `retry_limit` is spent. The direction prose and the canvases from Design Context are required input (`common.json#/$defs/designContext`); the DNA itself is carried for provenance and not shown to the model. Operations: `POST /v1/propose-jobs` (a model proposes a landing `composition.json` from a brief; the one output people are expected to edit), `POST /v1/materializations` (deterministic: brief + composition → landing Site AST and content, with the terms and privacy pages from fixed legal templates), `POST /v1/author-jobs` (Site AST + content + Design Context → `snapshot.json`), and `GET /v1/neo-styler-jobs/{job}`. Snapshot pages carry a complete HTML document and its stylesheet and map one-to-one onto Static Builder request pages and assets. The hearing a landing page needs is not fixed in the service: `tests/fixtures/neo-styler/landing-intake-template.json` is a Generic Intake template an orchestrator registers with Interview, and `brief` is the `path`-keyed values an intake session returns.

Wireframe AST v2 is the opt-in, content-bearing Tier 0 information-architecture contract. It keeps the outer HTTP `contract_version` at `1.0` and does not replace the existing default Wireframe AST v1 response. Each v2 page preserves a canonical Site AST key, path, and title, then uses a recursive `Region` tree whose terminal nodes are concrete `Text`, `Image`, `Link`, `Button`, `Input`, `Textarea`, `Select`, or `Checkbox` values. The closed schema fixes the finite semantic, layout, AIDMA-stage, emphasis, text-role, media-aspect, input-type, and action vocabularies. The owning Wireframe service additionally validates Site AST identity, unique paths and node IDs, document/main/section ancestry, exactly one page heading, list and form boundaries, local-link resolution, form names and submit semantics, and aggregate depth/node limits. v2 contains reviewable locale copy and field labels but no HTML, CSS, design tokens, classes, asset URLs, scripts, or provider configuration. A separate deterministic renderer may apply its server-owned neutral preview decoration; that decoration is not part of this AST contract.

Layout Snapshot 1.0 is the site-level, content-addressed geometry handoff between Wireframe and later styling. `schemas/v1/layout/snapshot.json` binds at most eight pages to the originating Structure digest, exact base64 source HTML bytes, a generic but explicitly versioned geometry-only Layout AST v2, its deterministic `mh-layout` CSS, and independent HTML/AST/CSS digests. A page keeps both its canonical URL `route` and generated HTML artifact `path`. Root constraints state container and content widths, numeric compact/medium/wide thresholds, 390/768/1440 verification widths, a minimum 44px action height, and single-column mobile source order. Wireframe review CSS, paint, decoration, and motion are outside the snapshot.

Creation always returns a new `candidate` whose site validation is `pending`, has a null subject, and lists every page exactly once with pending breakpoint and geometry outcomes at 390, 768, and 1440 CSS pixels. Preview validates each referenced page in a real browser through `preview/layout-validation-request.json` and returns the candidate-bound `page_validation`; the request carries the exact Layout AST so geometry findings can name real rules instead of trusting DOM metadata alone. Preview canonicalizes that AST, verifies its SHA-256 against the reference, requires its embedded constraints to equal the snapshot/root constraints, and invokes the Layout package's full validator before browser inspection. Contract 1.1 adds explicit signal coverage and breakpoint-continuity evidence; contract 1.2 requires `local_puppeteer` or `cloudflare_browser_run_cdp` and signs the exact result with a short-lived receipt before Styler can consume it. The Layout service aggregates all pages. Freezing creates a second immutable `frozen` snapshot only from a fully passed aggregate, leaves every page and constraint unchanged, and records exactly one `attach_validation` lineage operation from the candidate digest to the canonical validation digest. Failed validation remains a standalone result and is never embedded in a snapshot.

Snapshot identity is deterministic: remove `snapshot_id` and `snapshot_digest`, recursively sort object keys bytewise while preserving array order, JSON-encode with unescaped Unicode and slashes plus preserved zero fractions, and SHA-256 the resulting bytes; `snapshot_id` is `ls_` followed by that lowercase digest. `reference.json` selects one candidate or frozen page while repeating the snapshot, HTML, AST, and CSS identities; consumers decide which lifecycle state they permit. The Wireframe Presenter accepts either state for review, while Styler accepts only frozen snapshots. Create, freeze/get, Preview page validation, and Wireframe presentation envelopes live beside their owning schemas. Approval accepts `layout_snapshot` as an additive immutable artifact type.

Layout-only visual corrections are recorded in lineage as `apply_finite_layout_patch`. `layout/patch-snapshot-request.json` selects one page and accepts only a non-empty, digest-bound Layout patch plan; `layout/patch-snapshot-result.json` reuses the write-once resource envelope but permits only a new `candidate` with `pending` validation. A finite-patch delta repeats that exact plan once at its root, derives `change_id` as `layout-patch-<SHA-256>` from its canonical JSON, and contains only `apply_finite_layout_patch` operations. Every operation embeds the corresponding plan issue at the same sequence and must change its bound digest. Page-rule operations target one `page_key` and record the selected page Layout AST before/after digests; the `$constraints` operations (`set_container_max_width`, `set_content_max_width`, and `set_minimum_action_height`) target site constraints and record root constraints before/after digests. Legacy deltas cannot carry a root `patch_plan`, and legacy operations cannot carry `finite_patch`, so arbitrary CSS, prose rewrites, and later-stage Skin/Decor/Motion operations cannot enter the Layout snapshot through this audit trail.

Visual review uses `schemas/v1/visual-feedback/patch-plan.json` as a shared deterministic correction language for Layout, Skin, Decor, and Motion. A plan binds the base AST digest and contains zero to twenty issues. `review-result.verdict` is `patch_required` only when the bounded loop permits a non-empty finite patch, `passed` when the plan is empty and quality gates pass, and `human_review_required` when automatic convergence must stop. Each correction names an AST rule, a bounded viewport, a finite problem slug, and one stage-owned operation whose value has a type-specific schema. For Layout, `{ "min_width": 320 }` is the canonical all-device/base scope; compact, medium, and wide ranges map to their named responsive scopes, and ambiguous ranges crossing breakpoints fail closed. Token-wide Skin/Decor operations and all Motion operations also require this all-device scope because their AST dialects do not expose responsive storage for those values. Mobile order is not a public v1 patch operation while Layout v2 freezes `preserve_source_order=true`. The Layout reviewer resolves only a pending candidate that can receive the next finite patch; frozen Layout is immutable and is consumed downstream instead. Skin, Decor, and Motion resolve an immutable Stage Bundle through `stage_subject_ref`, and the Layout/non-Layout subject shapes are mutually exclusive. The companion patch request/result schemas report an exact before/after digest delta and do not accept free-form rewrite instructions or arbitrary CSS patches.

The reviewer returns the exact shared Design Core 1.1 `scorecard` and `decision`. `design-quality-evaluation.json` fuses three independently digest-bound sources: deterministic CDP/browser evidence, Screenshot Reviewer observations, and an objective-bound agentic assessment. CDP owns structural, responsive, accessibility, and operability evidence; it cannot approve by itself. Browser and Screenshot Reviewer must both pass readability, Screenshot Reviewer owns visual hierarchy and Order/Richness observations, and the agentic source owns Purpose Fit, information priority, and primary-action clarity. The deterministic scorer keeps Order, Richness, Purpose Fit, and Accessibility separate; Core is `sqrt(Order × Richness)` and Final is `Core × PurposeFit / 100`, calculated in integer basis points. Every evidence source, the frozen subject, objective, rubric, aggregate evidence, and scorecard are digest-bound, and missing coverage or any non-passing hard-gate outcome fails closed.

`loop_context` is the exact sealed Design Core policy state. It is server-owned: a service either loads it from its own store or accepts it only through service-authenticated transport; `state_digest` is canonical integrity, not authentication. Policy 1.1 separates a maximum of four evaluations from a maximum of three accepted patches, so the third patch can still receive a final evaluation. Model calls and elapsed time are separately bounded. The exact `decision` stops on incomplete evidence, no finite patch, patch no-op, subject cycle, exhausted budgets, regression, repeated issue sets, or a score plateau, preserves the best artifact seen, and returns `human_review_required` instead of asking an agent to invent a new design direction.

Non-Layout visual review never accepts a caller-transported Stage Bundle as subject authority. A succeeded Skin, Decor, or Motion job—and every immutable finite-patch revision—returns `stage_subject_ref` with profile `styler-stage-subject-reference-v1`. The reviewer accepts that closed reference, resolves the Stage Bundle from the Styler service's own store, and verifies the exact job, stage, context digest, and AST digest. The full Stage Bundle remains the downstream generation/rendering handoff, while Layout continues to use `layout_snapshot_ref`.

Every service-review screenshot is provenance-bound to the Preview resource UUID, its stored `snapshot_id`, its safe relative HTML `entry_path`, renderer, requested viewport, full-page mode, decoded image digest, and capture state. Preview screenshot contract `1.3` is the visual-feedback default: Preview signs those exact claims in a short-lived `capture_receipt`; `1.0` through `1.2` remain readable for existing clients but are not accepted as new Reviewer evidence. Layout review requires the Preview snapshot identity to equal the referenced Layout Snapshot ID. Skin, Decor, and Motion review use `ast_<base_ast_digest>` as the Preview snapshot identity. Screenshot dimensions are checked from the image bytes, and the `(viewport, capture_state)` signature is unique inside a review. The service route accepts only server-renderable `rest` or elapsed `enter` captures with a null target. Interactive states stay in the local in-app agent route and do not claim Preview-service provenance.

`preview/browser-evidence-request.json` is the cloud/local automated-review route. It runs one Puppeteer/CDP session and returns three to ten signed screenshots plus the matching DOM geometry and Accessibility Tree counters in `browser-evidence-result.json`; rest captures at 390, 768, and 1440 CSS pixels are mandatory. The HMAC-bound `visual-feedback/browser-evidence.json` repeats the Preview, Snapshot, entry, stage subject, every screenshot digest, provider, raw samples/violations/metrics, four deterministic gates, and evidence lifetime. `standalone_approval=false` is invariant: CDP evidence is necessary for an automated pass but remains insufficient without the Screenshot Reviewer and fixed-objective agentic source. Omitting `browser_evidence` from a legacy-compatible review request therefore fails evidence coverage closed.

The public visual-feedback route inventory is: Layout Snapshot candidate create/get/finite-patch/freeze, Wireframe presentation, Preview Layout geometry validation, signed screenshot `1.3`, same-run signed Browser Evidence, asynchronous Styler visual review create/get, and Skin/Decor/Motion finite patch application. After freeze, the direct route sends the reference to Styler pipeline contract `1.3`; it resolves and reuses the exact Layout AST/CSS, then runs Skin, Decor, and Motion without an external pause between stages. The per-stage visual route instead hydrates that reference through Styler Layout contract `1.3`, then runs separate Skin, Decor, and optional Motion generate/review/finite-patch loops. It does not pause an active pipeline job. The asynchronous pipeline and reviewer resources are described by `schemas/v1/styler/pipeline-job.json` and `schemas/v1/visual-feedback/review-job.json`.

Illustration is a Tier 1 semantic material catalog built over the Tier 0 Image Adapter. Its finite Illustration Specification is shared by generation and search; the service compiles that specification into a provider-neutral prompt, imports successful image bytes into its own storage, and never exposes an upstream provider URL.

Site Edit is a Tier 1 deterministic transformation service. Target inspection accepts caller-supplied HTML and returns at most 200 bounded text, image, and contact-link candidates with canonical XPath targets. Candidate IDs are request-local, and `base_digest` binds the exact inspected HTML bytes to a later edit request. Inspection is synchronous and performs no persistence, external communication, or mutation; `truncated` reports either omitted candidates or shortened display fields.

Interview is a Tier 1 private authoring capability that runs a bounded scripted intake or imports an already collected website brief. Its versioned API starts, reads, advances, imports, and deletes interview sessions; completed structured data contains organization, goals, audience, tone, and optional requirements and materials. It does not generate a site, copy, media, or public content. Start and answer require a bounded Idempotency-Key and replay the original response for an exact retry. Answer also requires `expected_step`, so stale or concurrent UI events return 409 without being applied to a later question. Import keeps its optional legacy Idempotency-Key behavior.

Template is a Tier 1 deterministic document-template source of truth. It converts Markdown into self-contained HTML, inspects explicit `m-field` annotations into a `path`-keyed field manifest and JSON Schema, persists semantically immutable template versions, and binds validated values into the stored version without re-inspection. Version identity covers the exact HTML, canonical manifest, semantic metadata, and contract version. Template does not infer annotations, run interviews, render PDFs, or own document-specific calculations and repeaters.

Resource Contract AST is the closed, deterministic intermediate representation between an HTML `m-*` scanner and display, form, administration, or API projection. It models Content (`m-content`), Collection (`m-post` plus `m-item`/`m-key`), and Form (`m-form` plus successful controls) as mutually exclusive resource kinds, and retains provenance for every marker-derived field, constraint, capability, and binding. Resource, field, DOM-binding, provenance, and input-option arrays preserve source order because that order is presentation meaning needed for a display/admin/form round trip; only set-like arrays such as capabilities, diagnostics, diagnostic blocks, and source inventory use their documented stable sort. Object keys use canonical sorting during deterministic serialization. A scanner always emits a `proposal` and never invents Content/Collection writes. A trusted host may enrich it with field input presentation and explicit `create`, `update`, `delete`, or `upsert` bindings, while every write binding keeps confirmation `unresolved` until the host explicitly selects `required` or `not_required`. Authentication, authorization, tenant scope, storage, server validation, audit, write semantics, and concurrency likewise remain unresolved until the trusted host supplies references to explicit policy definitions. Only an `operational` AST with every policy and write confirmation resolved, an explicit source/action/operation binding, and no blocking diagnostic is eligible for API or write-capable administration projection. Policy references are identifiers only: credentials, tokens, connection strings, secret values, and provider configuration must never enter the AST. Arbitrary unmarked HTML therefore remains a rejected proposal rather than becoming an API. `domain/resource.json` and `forms/definition.json` remain downstream service payloads and must be derived from this AST instead of becoming competing scan representations.

Presentation is a Tier 0 synchronous, deterministic, and side-effect-free materialization capability. Its provider-neutral Component AST contains only finite compositions, variants, semantic slots, literal or Resource Contract field bindings, action intent, icon intent, and relative asset references. A server-owned adapter registry resolves an explicit version-pinned Adapter Profile into canonical HTML, compiled CSS, immutable required-asset metadata, and a source map. The service never accepts CSS classes, executable templates, class names, package URLs, provider credentials, arbitrary remote assets, or remote catalog lookup instructions from a request. Tailwind CSS and Heroicons may be built-in open-source adapters; proprietary Tailwind Plus component code is accepted only through a private bring-your-own catalog registered by the host and is never redistributed by the shared contract or default service. Image and self-hosted font bytes remain owned by Media or another explicit asset service; Presentation receives only normalized relative paths and SHA-256 digests and never fetches them. Commercial Google Fonts self-hosting uses the `licensed-self-hosted` adapter and a closed Font Asset Set that pins the `google/fonts` revision, family path, SPDX license, copyright and license-text digests, Reserved Font Names, transformation history, and governed WOFF2 asset references. The policy check is deterministic technical validation rather than legal advice; it rejects undeclared or unsafe transformations before materialization.

Generic Intake extends the Tier 1 Interview boundary by accepting the same `path`-keyed field definitions emitted by Template. Immutable intake definitions create idempotent chat or form sessions and return temporary signed browser URLs; confirmed values are read back through the authenticated service API. The existing fixed website-brief Interview API remains a separate compatible surface.

Knowledge is a Tier 1 private retrieval capability isolated by tenant and knowledge base. Callers or dedicated source adapters resolve documents into bounded file bytes and metadata before ingestion; Knowledge never fetches an arbitrary remote URL, stores source credentials, or owns LINE WORKS, Slack, or another messaging surface. Idempotent multipart ingestion extracts, chunks, and indexes documents asynchronously. A scoped document lifecycle endpoint lets trusted callers delete one indexed document and its chunks without teaching Knowledge anything about the upstream source. Search uses the versioned `weighted_rrf_v1` hybrid ranking contract with a stable chunk-ID tie-break. Answering defaults to the only v1 grounding policy, `strict_grounded`, and returns cited evidence or an explicit refusal rather than an unsupported answer.

Knowledge Source is a Tier 2 edge orchestration capability over Tier 1 Knowledge. It stores Drive, WordPress, Storage, and LINE WORKS credentials only as encrypted write-only connection state, permits RSS without credentials, resolves public remote content into bounded bytes, and hands those bytes to Knowledge through its existing multipart contract. Pull drivers are Google Drive, RSS, WordPress, and S3-compatible Storage; LINE WORKS is a signed, freshness-checked, deduplicated webhook driver. Exhaustive sources remove stale Knowledge documents through the source-agnostic document lifecycle API, while partial RSS and event streams never infer deletion from absence.

CRM is a Tier 1 tenant-isolated company and person directory. Its ten Bearer-authenticated operations list, create, read, update, and soft-delete each resource. Every write requires JSON plus an 8–200 character `Idempotency-Key`; exact completed retries return the original status and body with `Idempotent-Replayed`, while changed input, another operation, or active work returns 409. Updates and deletes require `expected_version` and return 409 on stale state. A person may reference only an active company in the same tenant, and all cross-tenant resource lookups are indistinguishable from missing records. List queries expose bounded literal search, finite sort/direction, stable UUID tie-breaking, and page sizes from 1 to 100.

Messaging is a Tier 1 tenant-isolated state and delivery boundary for normalized channels, conversations, and messages. Its eight service operations require Bearer authentication; all three service writes require JSON and a bounded `Idempotency-Key`, replay completed responses, and never deliver twice on an exact retry. Channel credential references are encrypted and write-only. Both outbound tokens and inbound signing secrets are resolved only at runtime from an active channel and an exact tenant/provider-scoped credential entry; missing or mismatched scope fails closed. Provider envelopes and secrets are never exposed. Local and Slack outbound delivery are supported; Slack is fixed to `https://slack.com/api/chat.postMessage`. Delivery executes once with no automatic retry: confirmed success is `sent`, a definite provider rejection is `failed`, and transport, 5xx, redirect, or malformed success ambiguity is `unknown` and requires reconciliation before any retry. Messaging owns no CRM company or person data. The ninth operation ingests Slack webhooks without Bearer auth only after verifying the v0 HMAC over the exact raw body and a timestamp within 300 seconds. It caps payloads at 262,144 bytes, deduplicates each channel/event ID against the raw-body SHA-256, rejects changed replays, stores only normalized fields, and treats callback or response URLs as inert non-runnable data that is neither fetched nor persisted.

Channel is a Tier 1 tenant-isolated outbound publishing boundary for X, Threads, Instagram, LINE, and YouTube. Its eleven Bearer-authenticated scoped operations manage encrypted write-only provider connections, read-only identity verification, private bounded MP4 artifacts, and normalized asynchronous publication state. All six writes require an 8–200 character `Idempotency-Key`; connection update, delete, and verification also require `expected_version`. Exact retries replay their stored response without another provider call or queue job. Every provider endpoint is server-owned. Delivery runs once with no automatic retry after dispatch: confirmed completion is `succeeded`, definite rejection is `failed`, and any ambiguous completion is `unknown` and must be reconciled before a new publication. YouTube accepts only a tenant-owned private artifact, initiates one resumable session at Google's fixed endpoint, strictly validates the returned HTTPS upload location, and performs one streamed PUT without automatic status-query or resume. Caller filesystem paths and video URLs are never accepted or fetched, and storage paths, credentials, and raw provider envelopes never cross the public interface.

Measurement is a Tier 1 tenant-isolated reporting and controlled-write boundary for GA4, Search Console, Google Tag Manager, and Google Business Profile. Its eleven Bearer-authenticated operations manage encrypted write-only connection credentials, fixed server-owned Google endpoints, bounded report and resource reads, and GTM/GBP mutations. Connection CRUD and read-only reports do not claim replay or optimistic-write semantics they do not implement. A provider mutation alone requires an 8–200 byte `Idempotency-Key`, a reviewed live `expected_version`, and a SHA-256 confirmation digest of the canonical provider, operation, resource, version, and payload summary. Exact completed retries return the stored response without another provider call. An ambiguous provider outcome remains in processing state and returns 409 on retry until an operator reconciles it; automatic external mutation retry is forbidden. Credentials, token cache material, connection revisions, raw provider errors, and caller-selected endpoints never cross the public interface. Read requests cap date range, dimensions, metrics, rows, offsets, page sizes, tokens, and provider response bytes.

Site Source is the isolated remote-acquisition boundary for existing sites. Tenant- and site-scoped GitHub, SFTP, FTPS, and FTP connection credentials are encrypted at rest and never returned. GitHub uses the fixed public GitHub API; server drivers accept only public destinations and fixed protocol ports, SFTP requires a pinned host-key fingerprint, and FTPS requires peer verification. Plain FTP remains in the legacy interoperability contract but is disabled by default and requires an explicit deployment opt-in. An idempotent asynchronous fetch resolves one configured root into an immutable self-contained snapshot containing normalized relative paths, detected MIME types, base64 bytes, per-file SHA-256 digests, and a canonical manifest digest. File count, per-file bytes, total bytes, and provider time are bounded. Traversal, symlinks, Git submodules and metadata, secret files, and server-executable files fail the whole fetch and leave no snapshot. Site Import consumes these resolved snapshots and never owns remote credentials or opens remote connections.

Approval is a Tier 1 decision boundary for immutable artifact versions. It owns tenant- and site-scoped review requests, attributed conversation, the first final decision, required write idempotency, and keyed audit verification. It never fetches the artifact or its descriptive preview URL. Its Bearer principal is a trusted service; the caller remains responsible for end-user authentication, tenant authorization, and truthful actor assertions.

Site Change is a Tier 2 execution boundary for tenant- and site-scoped GitHub repositories. It registers or provisions repositories through a service-owned GitHub App mapping, creates one disposable workspace per asynchronous `site_content_v1` Codex run, enforces the existing finite content-edit policy, and emits an immutable canonical diff digest. Its public contract accepts neither credentials, remote URLs, Git refs, nor shell commands. Instructions are write-only and ordinary responses and audit payloads retain only their SHA-256 digest. It can push its server-owned branch or create a pull request. Approval owns only the external review decision; Site Change owns technical merge eligibility. Merge execution re-resolves Approval from fixed service configuration, requires an integrity-valid approved `site_change` artifact matching the change ID, head SHA, and diff digest, and independently verifies the live base. A changed base SHA or conflict fails closed without automatic rebase or conflict resolution.

The completed Site Change merge result is also available through an authenticated side-effect-free read on the same `merges` resource. It exposes the immutable `merge_sha` and `merged_at`, allowing an orchestrator to reconcile a lost mutation response or observe a merge initiated by another trusted client without repeating any GitHub mutation.

Document is a Tier 0 isolated rendering capability. Safe HTML preview is synchronous and side-effect free; PDF rendering is an idempotent asynchronous job with an authenticated status and artifact endpoint. The source HTML owns page size, orientation, and margins through CSS `@page` unless the request explicitly supplies `format`, `landscape`, or `margins`; those fields remain available as renderer overrides for existing integrations. `print_background` and `page_ranges` do not change page ownership. Job responses may report `page_source` as `css` or `renderer`; its absence identifies a legacy response and is interpreted as `renderer`, while the required legacy `format` field is only a fallback when `page_source` is `css`. HTML is treated as untrusted: executable or embedded content and external/local resources are rejected, JavaScript and redirects are disabled, outbound browser requests and host resolution are blocked, and a restrictive sandboxed CSP is injected. Generated PDF bytes remain on Document-owned private storage and expire with the job.

All OpenAPI paths are relative to the independently deployed service's `/api` base path. For example, `/v1/builds` describes the externally reachable `/api/v1/builds` route. This convention is shared by Tier 0 through Tier 3.

HTML Email Builder is a synchronous, deterministic, side-effect-free transformation. It requires service Bearer authentication and a closed request body, but no Idempotency-Key; identical payloads produce the same digest. Delivery remains a separate capability.

Deploy is the Tier 3 release boundary for immutable Static Builder artifacts. It owns tenant- and site-scoped provider environments, encrypts credentials at rest, and never returns credential values. GitHub and Cloudflare Pages support `preview`, `staging`, and `production`; SFTP and FTPS are limited to `preview` and `staging` in v1 because those drivers do not provide atomic cutover and rollback. Every environment targets a dedicated managed subtree: GitHub repository root and the SFTP/FTPS `/` root are forbidden deployment targets, and remote root paths are capped at 1700 characters so derived destinations remain within the 2048-character persistence boundary. Every write is idempotent. A deployment request accepts only a build UUID, SHA-256 manifest digest, and Approval request UUID; the service resolves both records from fixed service-configured APIs and rejects caller-supplied URLs. It deploys only a succeeded build whose digest matches an approved, matching artifact with a server-verified valid Approval history.
